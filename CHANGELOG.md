# Changelog

## 1.0.0 (12 November 2026)

- First build of Module 28's project from its code seed: Gradle 9.9.1 wrapper, version catalog, lockfiles, Spotless with google-java-format 2.0.0, JaCoCo 0.8.16 with a 0.80 line floor, one task per program, `drillClasspath` for the drills.
- The seed's single schema file is split: `db/common/V1__outbox.sql` (the outbox, its partial index, the relay's fence, the event-rule function) runs in all three databases; `db/inventory/` adds Module 13's catalog and holds (copied from `seatwave-transactions` at `d78af3a`, without `bookings`), the semantic lock and the lab's 40,000 seats; `db/payment/` adds `payments`; `db/booking/` adds `booking_sagas`, `bookings` (Module 35's `price_paid`), Module 27's `processed_messages` and the read model `bookings_by_customer`. The seed's inventory change missed that Module 13's `only_active_holds_are_open` check would refuse every CONFIRMING hold; it is now `only_open_holds_have_no_end`, counting ACTIVE and CONFIRMING as open.
- `BookingSaga` now drives a `SagaStore` and `SagaParticipants` instead of the in-memory classes, so the same transition table runs the programs, the unit tests and the real services: `ServiceDatabaseSagaStore` and `LocalParticipants` in memory, `JdbcSagaStore` and `HttpParticipants` on the stack. The saga's row became the record `SagaRecord`. `StepReply`, `BookingSaga`'s types and `BookingsByCustomer` became public for the adapters; `ReadModelCli`'s events moved to `BookingHistory`, shared with the rebuild drill. The five programs print exactly what the seed printed (`ProgramOutputTest`).
- `PostgresKafkaRelay` is compiled against `kafka-clients` 4.4.0: it adds `type`, `schema_version`, `aggregate_version` and a `message_id` fixed by the outbox id to every record, routes event types to topics (the booking outbox sends its final events to `seatwave.bookings` and its commands to `seatwave.saga.commands`), returns a `Pass` that says when it was fenced, and takes a hook between the acknowledgement and the mark, which the drills use to kill it there. `RelayLoop` runs it every 100 ms in each service.
- Added: the payment provider's stub (`stub/PaymentProviderStub`, JDK only, built by `stub/Dockerfile` into a non-root image) with idempotency keys, scripted declines and lost answers, latency, failing refunds and a ledger; `JdbcInventory`, `JdbcPayments`, `JdbcSagaStore`, `JdbcBookingsByCustomer`, `Outbox`; `CommandServer`, `HttpParticipants`, `ProviderClient`; the three services (`InventoryServiceCli`, `PaymentServiceCli`, `BookingServiceCli` with its resume-on-start and sweeper) and the drill tools (`RelayCli`, `DualWriteDrillCli`, `TopicAuditCli`, `OutboxLoadCli`, `HoldLoadCli`, `SagaDrillCli`, `ReadModelRebuildCli`, `TwoPhaseCommitDrillCli`, `StackCli`); `scripts/stack.sh` and `scripts/drill.sh`; the unit tests beside the seed's and the stack tests.
- The Compose file: one broker (the seed's choice, kept for memory: the Docker VM is shared), every container with a memory limit, the database password from a generated file in the ignored `.secrets/` instead of the shell, `max_prepared_transactions=8` on inventory and payment for the two-phase commit drill only, and the stub on 22820.
- Found by the runs and fixed before the measured ones: a producer with a 10-second delivery timeout let batches to a freshly created topic expire, after which its idempotent sequence had a gap the broker refused again and again; `Producers` keeps Kafka's request and delivery defaults, `StackClients.createTopic` waits for every partition's leader, and the rebuild drill's loader sends one request at a time. `OutboxLoadCli` now joins commit and arrival times at the end, because a fast relay delivered a few rows before their writer had noted the commit. The first 40-run loop of the test task beside busy loops failed once; its quiet log kept no test name, so the 200 ms client timeouts of `HttpCommandsTest`, the only timing margins in the unit tests, were raised to 2 s and the loop was run again.
